Project 01
Task Manager API

A full REST API for task management with user authentication, built from scratch in C# using ASP.NET Core. Users can register, log in, and manage their own tasks with full create, read, update, and delete functionality. Tasks support filtering by status and priority, pagination, and a statistics endpoint that returns aggregated breakdowns of a user's workload.

REST APIC#ASP.NET CoreJWT AuthBackend
Developer Notes
I built this project to practice real backend development patterns that come up in almost every junior developer job posting. The two things I wanted to nail were authentication and clean architecture. For auth I implemented JWT Bearer tokens with BCrypt password hashing, which meant learning how token expiry, signing keys, and claim-based identity actually work under the hood rather than just using a library blindly. For architecture I used a repository pattern to separate data access from the API layer — the idea being that you could swap the in-memory store for a real database like PostgreSQL with EF Core and the endpoints themselves would not need to change. I also paid attention to returning the right HTTP status codes for each case rather than just returning 200 for everything, which is something I noticed a lot of beginner API tutorials skip over entirely.
Type: Solo Project
Language: C#
Framework: ASP.NET Core
Technical Details
ASP.NET Core JWT BCrypt REST Repository Pattern
  • Implemented JWT Bearer authentication with signed tokens, claim-based user identity, and a 7-day expiry — all validated on every protected endpoint automatically via the ASP.NET middleware pipeline.
  • Used BCrypt password hashing for secure user registration and login, ensuring passwords are never stored in plain text and are resistant to brute force via salt rounds.
  • Built a repository pattern that decouples the data layer from the API layer — the in-memory store can be swapped for EF Core and a real database without touching any endpoint logic.
  • Created a statistics endpoint that uses LINQ grouping to return task breakdowns by status, priority, and overdue count in a single query rather than multiple round trips.
Code Example
Program.cs C# — JWT Auth + Task Endpoint 
// Login: validate credentials, return signed JWT
app.MapPost("/auth/login", (LoginRequest req, UserRepository users) =>
{
    var user = users.GetByUsername(req.Username);
    if (user is null || !users.VerifyPassword(req.Password, user.PasswordHash))
        return Results.Unauthorized();

    var token = GenerateToken(user.Id, user.Username, jwtKey, jwtIssuer);
    return Results.Ok(new { token, user.Username });
});

// Get tasks: filter by status/priority, paginate results
app.MapGet("/tasks", [Authorize] (ClaimsPrincipal principal,
    TaskRepository tasks, string? status, string? priority,
    int page = 1, int pageSize = 10) =>
{
    var userId = principal.FindFirstValue(ClaimTypes.NameIdentifier)!;
    var userTasks = tasks.GetByUser(userId);

    if (status is not null)
        userTasks = userTasks.Where(t =>
            t.Status.Equals(status, StringComparison.OrdinalIgnoreCase)).ToList();

    var total = userTasks.Count;
    var paged = userTasks.Skip((page - 1) * pageSize).Take(pageSize).ToList();
    return Results.Ok(new { total, page, pageSize, data = paged });
});
Code Explanation
The login endpoint validates the user's credentials against the stored BCrypt hash and, if they match, generates a signed JWT containing the user's ID and username as claims. That token is then sent back to the client and included in the Authorization header on every subsequent request. The task retrieval endpoint uses the [Authorize] attribute to automatically reject unauthenticated requests before my code even runs — ASP.NET's middleware handles that. Once past auth, I extract the user's ID from the token claims, pull only their tasks, and apply optional filters before paginating. The result includes the total count alongside the page so the client can calculate how many pages exist without making a second request. I kept each endpoint as a small focused function rather than putting everything into a single large controller, which makes it straightforward to read and test each route independently.

Project 02
Personal Finance Tracker

A console application for tracking personal income and expenses, built in C#. Transactions are categorized across 8 expense types and 5 income types, and persist between sessions using JSON file storage. The app generates real-time summaries showing net balance, monthly breakdowns, and an ASCII bar chart of spending by category.

C#.NET 8Console AppJSON StorageLINQ
Developer Notes
I built the Finance Tracker to practice working with persistent data outside of a database — using JSON file storage with System.Text.Json. The main design challenge was making the data model clean enough that adding new transaction types or categories later would not require rewriting half the application. I ended up using enums for transaction types and string arrays for categories, which kept the code simple while still being extensible. The ASCII bar chart in the category breakdown was something I added because I wanted a way to visualize spending proportionally without pulling in a charting library — it scales each bar relative to the highest spending category so the comparison is always meaningful regardless of the actual amounts involved. I also made a deliberate decision to keep all UI in its own method and all data logic in the repository class, which is a habit I was building toward the kind of separation of concerns you need in larger projects.
Type: Solo Project
Language: C#
Storage: JSON
Technical Details
C# .NET 8 System.Text.Json LINQ
  • Used System.Text.Json to serialize and deserialize the full transaction list to disk on every add or delete, keeping data intact between application sessions without needing a database.
  • Built a proportional ASCII bar chart that scales each category's bar relative to the highest spending category, giving a meaningful visual comparison at any scale of spending.
  • Used LINQ grouping and aggregation for the summary and breakdown views — filtering by month, grouping by category, and summing amounts without manual loops.
  • Structured the app around a clean separation between UI rendering and data logic, keeping the repository class responsible only for data and the app class responsible only for display.
Code Example
Program.cs C# — Category Breakdown + JSON Save 
// ASCII bar chart scaled to highest category
private void ShowCategoryBreakdown()
{
    var grouped = _transactions
        .Where(t => t.Type == TransactionType.Expense)
        .GroupBy(t => t.Category)
        .Select(g => new { Category = g.Key, Total = g.Sum(t => t.Amount) })
        .OrderByDescending(g => g.Total)
        .ToList();

    var max = grouped.Max(g => g.Total);

    foreach (var g in grouped)
    {
        var barLen = (int)((g.Total / max) * 30);
        var bar = new string('█', barLen);
        Console.WriteLine($"  {g.Category,-15} {bar,-30} ${g.Total:F2}");
    }
}

// Persist all transactions to disk as JSON
private void SaveData()
{
    var json = JsonSerializer.Serialize(_transactions,
        new JsonSerializerOptions { WriteIndented = true });
    File.WriteAllText(_dbPath, json);
}
Code Explanation
The category breakdown chains LINQ operations to filter only expenses, group them by category, sum each group, and sort by total in a single readable expression — no manual loops needed. The bar length for each category is calculated as a proportion of the highest spending category scaled to 30 characters, which means the chart always fills the available space meaningfully regardless of whether you spent $10 or $10,000. The save method serializes the entire transaction list to indented JSON every time a change is made. I chose to write indented JSON rather than compact JSON because it makes the storage file human-readable, which is useful for debugging and also shows that I was thinking about the developer experience of working with the data, not just the minimum that would work.

Anime & Game Dashboard

A Python data pipeline that fetches live top anime rankings from the MyAnimeList API and top Steam game statistics from SteamSpy, normalizes and displays the data in a formatted terminal view, and generates a self-contained HTML dashboard with interactive Chart.js bar charts that opens automatically in the browser.

PythonREST APIsData PipelineHTMLJavaScriptChart.js
Developer Notes
I built this project because I wanted to practice consuming third-party APIs and transforming raw data into something presentable — which is a task that comes up constantly in real software jobs. The interesting constraint here was that I was hitting two completely different APIs with different response shapes and had to normalize them into consistent display models before rendering. I also wanted the output to be genuinely useful rather than just a terminal dump, so I built the HTML dashboard generator in Python — it produces a self-contained file with embedded Chart.js charts and a dark-themed data table that you can open anywhere without needing a server. The error handling was something I put real thought into: if either API is unreachable the application falls back to cached sample data and continues running rather than crashing, which is the kind of resilience that matters in production applications. I used the rich library for the terminal output because I wanted to practice using third-party libraries properly and because it made the output significantly more readable.

Language: Python
Output: Terminal + HTML

Python Requests Rich Chart.js HTML Generation
  • Consumed two live third-party REST APIs simultaneously — Jikan (MyAnimeList) and SteamSpy — normalizing their different response structures into consistent internal data models before rendering.
  • Built a graceful fallback system that catches network errors and automatically switches to cached sample data, keeping the application functional when external APIs are unreachable.
  • Generated a self-contained HTML dashboard from Python — embedding Chart.js bar charts and a full dark-themed data table into a single file that opens in the browser without needing a server.

Code Example
dashboard.py Python — API Fetch + Fallback 
def fetch_top_anime(limit: int = 20) -> list[dict]:
    url = f"https://api.jikan.moe/v4/top/anime?limit={limit}"
    try:
        r = requests.get(url, timeout=10)
        r.raise_for_status()
        data = r.json()
        return [
            {
                "rank":    i + 1,
                "title":   a["title"],
                "score":   a.get("score", 0) or 0,
                "genres":  ", ".join(
                    g["name"] for g in a.get("genres", [])[:3]
                ),
                "members": a.get("members", 0),
            }
            for i, a in enumerate(data.get("data", []))
        ]
    except requests.RequestException:
        return get_fallback_anime() # graceful fallback
Code Explanation
The fetch function hits the Jikan API with a timeout so it does not hang indefinitely on a slow connection. If the request succeeds, a list comprehension transforms the raw API response into a normalized dictionary format — pulling only the fields the application needs and providing safe defaults with .get() for any fields that might be missing from the response. The or 0 on the score handles the case where the API returns null for unscored entries, converting it to a usable number instead of crashing downstream. If anything goes wrong — network error, timeout, unexpected status code — the except block catches the RequestException and returns fallback data instead, so the rest of the application continues running as if the request had succeeded. This means the dashboard still generates and opens even when the API is completely unreachable.

Project 04
Portfolio Website

This portfolio website, built from scratch using HTML, CSS, and vanilla JavaScript. Features a tab-based project navigation system with URL hash routing, scroll-triggered reveal animations using the Intersection Observer API, animated skill bars, and a fully responsive layout. No frameworks or build tools — just hand-written code.

HTMLCSSJavaScriptResponsiveNo Framework
Developer Notes
I built this site from scratch rather than using a site builder because I wanted the portfolio itself to be a demonstration of frontend skills, not just a container for them. The tab navigation system uses URL hash routing so that each project has its own shareable link — clicking a tab updates the browser history and loading a hash directly activates the right tab without any flicker. The scroll animations use the Intersection Observer API rather than a scroll event listener, which is the modern performant way to trigger animations on element visibility without hammering the main thread on every scroll event. The skill bars animate when they scroll into view using the same observer. Everything is written in vanilla JavaScript with no dependencies, which I did deliberately to show that I understand the underlying browser APIs rather than relying on libraries to abstract them away.
Type: Solo Project
Languages: HTML, CSS, JS
Frameworks: None
Technical Details
HTML5 CSS3 Vanilla JS Intersection Observer Hash Routing
  • Built a tab navigation system with URL hash routing — each project tab updates the browser history so every project has a direct shareable link, and the correct tab is activated on page load by reading the URL hash.
  • Used the Intersection Observer API for scroll-triggered reveal animations and skill bar fills — more performant than scroll event listeners as it does not run on every scroll frame.
  • Implemented a CSS custom property theming system using variables for all colors, making the visual design consistent and easy to update from a single location.
  • Built fully responsive layout using CSS Grid with auto-fit columns that collapse to a single column on mobile without any JavaScript or media query breakpoint logic in JS.
Code Example
index.html JavaScript — Hash Routing + Intersection Observer 
// Tab activation with URL hash routing
function activateTab(tabId, updateHash = true) {
  tabBtns.forEach(b => b.classList.remove('active'));
  tabContents.forEach(c => c.classList.remove('active'));
  const btn = document.querySelector(`[data-tab="${tabId}"]`);
  const content = document.getElementById(tabId);
  btn?.classList.add('active');
  content?.classList.add('active');
  if (updateHash) {
    const hash = tabToHash[tabId];
    history.pushState(null, '', hash ? '#' + hash : location.pathname);
  }
}

// Scroll reveal using Intersection Observer
const revealObs = new IntersectionObserver((entries) => {
  entries.forEach((e, i) => {
    if (e.isIntersecting) {
      setTimeout(() => e.target.classList.add('visible'), i * 80);
      revealObs.unobserve(e.target);
    }
  });
}, { threshold: 0.12 });

document.querySelectorAll('.reveal').forEach(el => revealObs.observe(el));
Code Explanation
The tab system maintains a mapping between tab IDs and URL hashes, so switching tabs updates the browser history and every project has a unique URL. On page load the hash is read back and the correct tab is activated before anything renders, preventing flicker. The Intersection Observer watches for elements entering the viewport rather than listening to scroll events — the key difference is that the browser calls my callback only when visibility actually changes, not on every scroll frame, which keeps the page smooth even with many animated elements. The staggered setTimeout inside the callback adds an 80ms delay per element so multiple elements that enter the viewport at once reveal in sequence rather than all at once, which feels much more polished. Once an element has been revealed the observer stops watching it to avoid unnecessary callbacks later.
